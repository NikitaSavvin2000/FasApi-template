# Каноническая инструкция для любого AI-агента

Этот файл — единственный источник правил разработки для любого coding agent.
Он не зависит от конкретной IDE, модели или инструмента. Для работы по задаче
со ссылкой также обязателен `AGENT_TASK.md`.

## Первые действия по задаче

1. Прочитать задачу, этот файл, `AGENT_TASK.md` и
   `docs/architecture.md`.
2. Выполнить `git status --short` и сохранить чужие изменения.
3. Найти существующую реализацию через `rg` в `src/` и `tests/`.
4. Кратко описать внешнее поведение, слои и план. Для нетривиальной задачи
   использовать `.agent/task-template.md`.
5. Написать минимальный тест поведения, затем реализацию и проверку.

Явное требование пользователя важнее этого файла. Не расширяйте задачу без
необходимости, не добавляйте абстракции и зависимости «на будущее».

## Карта кода

| Что меняется | Расположение |
| --- | --- |
| Запуск `python main.py` | `main.py` в корне |
| Фабрика FastAPI, middleware, mounted API-версии | `src/fastapi_template/main.py` |
| Обработчики HTTP | `src/fastapi_template/api/vN/routes/` |
| HTTP-зависимости | `src/fastapi_template/api/dependencies.py` |
| Pydantic request/response DTO | `src/fastapi_template/schemas/` |
| Бизнес-правила без FastAPI | `src/fastapi_template/services/` |
| Доменные значения | `src/fastapi_template/models/` |
| Источник БД, подключения и репозитории | `src/fastapi_template/db/` |
| Настройки | `src/fastapi_template/configs/config.py` |
| Lifecycle, ошибки, middleware, логирование | `src/fastapi_template/core/` |
| SQL-шаблон и команды локальной БД | `local_services/` |
| Unit-тесты | `tests/unit/` |
| OpenAPI-контракт работающего сервиса | `tests/contracts/` |

Подробнее о связях слоёв: `docs/architecture.md`.

## Архитектурные границы

- Не помещать прикладную логику в route handler и не передавать туда `Request`
  или `Response` без обоснования.
- Не смешивать Pydantic DTO, доменные модели и модели хранения.
- Использовать абсолютные импорты от `fastapi_template`; не менять `sys.path`.
- Импорт модулей не запускает сервер, миграции и внешние подключения.
- Каждая новая или изменённая функция имеет русский docstring и типы.
- Новый внешний ввод получает ограничения, описание, пример и проверку ошибок.

## Конфигурация и БД

Все настройки живут в `configs/config.py`. Приоритет источников: программные
overrides → окружение → `.env` → YAML → defaults.

- `APP_LOCAL_DEVELOPMENT=true` создаёт и использует
  `local_services/local.sqlite3`.
- Если флаг отсутствует, его значение — `false`; тогда `database.url` в
  `config.yaml` обязательна.
- Не менять `.env`, `config.yaml`, `credential.yaml` без явного указания.
- Не удалять и не сбрасывать локальную БД без явной команды пользователя.
- Новый драйвер БД, ORM и миграции добавлять только вместе с конкретным
  репозиторием и задачей.

## API и контракты

- Публичный URL начинается с `/vN`; основная версия выводится из
  `[project].version`.
- `/v1/docs` и `/v2/docs` — независимые документации; их OpenAPI доступен по
  `/vN/openapi.json` и не хранится YAML-файлом в Git.
- Каждый endpoint получает уникальный `operation_id`, русские `summary` и
  `description`, типизированные DTO, примеры и корректные статусы.
- Контрактные тесты обходят живой OpenAPI универсально. Не добавлять списки
  конкретных endpoint-путей в эти тесты.
- Если задача вводит SSE, не буферизовать ответ, освобождать ресурсы в
  `finally` и проверять потоковый протокол отдельным HTTP-клиентом.

## Тестирование и проверка

Тест проверяет наблюдаемое правило «условие → действие → результат» и имеет
понятное имя для `pytest -v`. Не писать тесты ради покрытия или внутренней
реализации.

После активации `.venv` используйте единый сценарий:

```bash
python scripts/verify.py unit
python scripts/verify.py contracts
python scripts/verify.py check
python scripts/verify.py all
```

`all` выполняет lock-проверку, Ruff, mypy, полный pytest и сборку пакета.
Перед commit/push работают Git hooks; не обходить их через `--no-verify`.

## Критерий готовности

Перед передачей результата:

1. Запустить относящиеся к изменению тесты, затем `python scripts/verify.py all`.
2. Проверить `git diff --check`, отсутствие секретов и случайных файлов.
3. Сообщить, что изменено, какие проверки действительно прошли и что не
   проверялось с причиной.
