# Инструкция по выполнению задач

Этот файл применяется, когда пользователь даёт ссылку на задачу и просит
следовать `AGENT_TASK.md`. Перед работой обязательно прочитайте
[AGENT.md](AGENT.md): в нём описаны фактическая структура, слои и правила
размещения кода. Инструкции дополняют `AGENT.md`; при конфликте приоритет имеют
явное задание пользователя и более узкие правила репозитория.

## Цель работы

Изменение должно естественно встраиваться в существующий шаблон, а не
добавляться как изолированный код. Предпочтительны небольшие, типизированные и
проверяемые функции с ясной ответственностью. Не создавать абстракции,
директории, зависимости, интеграции или тесты без конкретной потребности задачи.

## Обязательный порядок работы

### 1. Разобрать задачу до написания кода

1. Прочитать задачу по переданной ссылке, `AGENT.md`, этот файл, затронутые
   модули и существующие тесты. Проверить `git status` и не перезаписывать чужие
   изменения.
2. Сформулировать ожидаемое внешнее поведение: входы, выходы, ошибки, побочные
   эффекты, ограничения и изменения HTTP/OpenAPI-контракта.
3. Декомпозировать работу на небольшие функции или изменения функций. Для
   каждого пункта определить ответственность, входные данные, результат,
   возможную ошибку и слой, которому он принадлежит.
4. До реализации искать похожие возможности через `rg` в `src/` и `tests/`.
   Переиспользовать или аккуратно расширять существующие сервисы, схемы,
   зависимости и утилиты. Не дублировать уже имеющуюся логику.
5. Составить короткий план выполнения в порядке зависимостей: схема/доменная
   функция → сервис → HTTP-обработчик → контракт и документация. Если задача
   заметная, сообщить эту декомпозицию перед изменениями.

## Размещение кода и импорты

Соблюдать фактическую структуру `src/fastapi_template/`:

| Что добавляется | Куда помещать |
| --- | --- |
| Корневая команда `python main.py` | `main.py`; только передача управления установленному пакету |
| Фабрика приложения, живая OpenAPI и middleware | `main.py` внутри пакета |
| Логика URL-версии из `[project].version` | `core/version.py` |
| HTTP-маршрут, query/path/header parsing, dependency injection | `api/v1/routes/` или `api/v2/routes/`; подключение — в соответствующий `router.py` |
| Общая сборка HTTP и зависимости | `api/router.py`, `api/dependencies.py` |
| Прикладное правило, не зависящее от FastAPI | `services/` |
| Pydantic DTO для публичных запросов, ответов и SSE | `schemas/` |
| Доменные значения без HTTP и хранения | `models/` |
| Внешний HTTP/SDK-клиент | `clients/` |
| Выбор источника БД, репозитории, подключения и модели хранения | `db/` |
| Локальная SQLite БД, SQL-шаблоны и утилита управления | `local_services/` |
| Настройки, их загрузка и валидация | только `configs/config.py` |
| Lifespan, middleware, ошибки, логирование | `core/` |
| Небольшая независимая функция без доменной ответственности | `utils/` |

Не помещать бизнес-логику в route handler, не передавать `Request`/`Response`
в сервис без необходимости и не смешивать API-схемы с моделями хранения. Не
менять `sys.path`; использовать абсолютные импорты от `fastapi_template` и
держать их без циклов. Импорт модуля не должен запускать сервер, открывать
соединение или выполнять миграции.

## TDD: тест до реализации

Для каждой новой или изменённой функции сначала написать проверку её поведения,
а затем реализацию. Работать маленькими итерациями:

1. Добавить один минимальный тест, который описывает полезный сценарий и падает
   без реализации.
2. Запустить только его.
3. Реализовать функцию или минимальное изменение функции.
4. Снова запустить тест; исправить код, если фактическое поведение не совпало с
   ожидаемым.
5. После завершения очередного пункта запустить относящийся набор тестов.

Выбирать каталог теста по характеру проверки:

- `tests/unit/` — функция, сервис, конфигурация или middleware изолированно;
- `tests/contracts/` — OpenAPI JSON запущенного сервиса, его ограничения,
  примеры и соответствие ответов контракту без списка конкретных путей;
- `tests/integration/` — настоящий HTTP-сервер, lifespan, streaming,
  выключение процесса и взаимодействие компонентов.

Тест проверяет конкретное наблюдаемое правило: **условие → действие → ожидаемый
результат**. Не добавлять тесты ради покрытия, внутренних деталей реализации или
тривиальных getter/setter-случаев. У каждого теста должно быть понятное имя,
которое видно в `pytest -v`, например
`test_process_rejects_text_longer_than_contract_limit`; при неочевидной причине
добавлять короткий docstring с ответом «зачем нужен этот сценарий».

## Правила реализации

- У каждой новой или изменённой функции должен быть краткий docstring: что она
  делает, а для неочевидного поведения — важные ограничения и побочные эффекты.
- Публичные функции, классы и границы слоёв типизировать. Соблюдать строгий
  `mypy`.
- Валидацию внешнего ввода задавать Pydantic-схемами: ограничивать строки,
  числа, массивы и дополнительные JSON-поля. Не подменять проверку полей
  проверкой размера всего тела запроса.
- Асинхронный обработчик не блокирует event loop. Блокирующий I/O переносить в
  подходящий потоковый пул; CPU-тяжёлую работу не маскировать под async.
- Для заменяемых HTTP-зависимостей использовать `api/dependencies.py`.
- Новая настройка добавляется в типизированную модель `Settings`, документируется
  в примерах конфигурации и использует префикс `APP_` с `__` для вложенности.
  Обычные данные — в `config.yaml`, секреты — в `credential.yaml`.
- Локальная БД использует `APP_LOCAL_DEVELOPMENT=true`, SQL-шаблон из
  `local_services/` и не коммитит созданный SQLite-файл. Если флаг отсутствует,
  его значение — `false`; тогда обязательна `database.url` из конфигурации.
  Конкретный драйвер и ORM добавлять только вместе с нужным репозиторием.
- Новый публичный route получает уникальный `operation_id`, русские `summary` и
  `description`, типизированные request/response схемы, примеры и явные
  ошибки. URL начинается с `/vN`; major-версия основной ветки берётся из
  `[project].version` в `pyproject.toml`.
- OpenAPI не хранится отдельным YAML-файлом: контрактный тест запускает сервис
  и получает `/vN/openapi.json`. Не добавляйте тесты с перечнем конкретных
  endpoint-путей; расширяйте универсальный обход операций спецификации.
- Для SSE сохранять потоковую выдачу: не собирать ответ целиком, ограничивать
  события и интервал, проверять отключение клиента и освобождать ресурсы в
  `finally`. Учитывать, что Swagger UI может показать результат после закрытия
  ответа: проверять отдельные SSE-кадры через `curl -N`, EventSource или
  потоковый HTTP-клиент.

## Окружение и запуск

Проект управляет зависимостями через uv. Сначала синхронизировать зафиксированное
окружение, затем активировать его. После активации запускать Python-инструменты
через `python -m`, без `PYTHONPATH=src`:

```bash
uv sync --locked --group dev
source .venv/bin/activate

python main.py
python -m pytest --no-cov -v tests/unit
python -m pytest -v
python -m mypy src
python -m pre_commit run --all-files
```

## Завершение задачи

Перед передачей результата:

1. Выполнить релевантные unit/contract/integration тесты, затем полный `pytest`.
2. Выполнить `uv lock --check`, Ruff format/lint, mypy и полный pytest, который
   проверит OpenAPI работающего сервиса.
3. При изменении пакета проверить `uv build`; при изменении Dockerfile и
   доступном Docker — сборку образа, `/v1/health/ready` и корректную остановку.
4. Проверить diff, отсутствие секретов, случайных файлов, неиспользуемого кода и
   дублирования. Не изменять `.env`, `config.yaml` и `credential.yaml` без
   прямого указания.
5. В итоговом сообщении кратко указать: что изменено, какие части были
   переиспользованы или почему их не нашлось, какие тесты добавлены и какие
   команды реально прошли. Отдельно назвать невыполненные проверки и причину.
